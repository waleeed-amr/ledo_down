🔴 أهم المشاكل التي وجدتها
1. download_semaphore لا يحد فعليًا عدد التحميلات

دي أهم نقطة في downloader.py.

عندك:

with download_semaphore:
    ...
    _update_db(ctx, status="downloading")

وبعدها يخرج من الـ with بينما التحميل نفسه يستمر خارج الـ semaphore. يعني الـ Semaphore يحمي فقط لحظة تغيير الحالة إلى downloading، ولا يحمي عملية التحميل.

فلو هدفك "حد أقصى تحميلين في نفس الوقت"، الكود الحالي لا يحقق ذلك.

الحل: الـ semaphore لازم يظل ممسوكًا طوال _run_ytdlp() أو تستخدم queue/worker pool حقيقي.

2. زر Pause في الـ Mini Monitor فيه Logic Bug

في mini_progress.js أنت تعرض فقط:

const active = allDownloads.filter(dl =>
    ['downloading', 'starting', 'processing'].includes(dl.status)
);

وفي نفس الوقت عند إنشاء العنصر لديك:

const isPaused = dl.status === 'paused';

لكن paused أصلاً لا يدخل في active، وبالتالي isPaused عمليًا لن تكون true في العناصر المعروضة.

والأسوأ: الـ backend عند Pause يغير الحالة فعلًا إلى paused.

النتيجة المحتملة:

تضغط Pause
الحالة تصبح paused
العنصر يختفي من الـ Mini Monitor
لا تحصل على Resume من نفس الواجهة.

دي محتاجة إعادة تصميم بسيطة للـ filter بحيث الـ paused downloads تظل ظاهرة.

3. Sorting حسب التاريخ شبه مكسور

في renderer.js:

return parseInt(b.id) - parseInt(a.id);

لكن الـ IDs عندك UUIDs، مثل:

f6112f0f9adbce3d...

وليس أرقامًا.

فـ:

parseInt("f6112f...")

ستعطي NaN.

والتعليق نفسه يقول:

rely on ID or DB order assuming larger ID is newer

وده افتراض غير صحيح مع UUID.

الأفضل: sort على created_at القادم من database.

🟠 Dead Code / كود غير مستغل
4. initVanta() أصبح Dead Code فعليًا

عندك:

let vantaEffect = null;

function initVanta() {
    if (vantaEffect) {
        ...
    }
}

والتعليق نفسه يقول إن Vanta تم تعطيله واستبداله بخلفية static.

لكن ما زلت تستدعي:

initVanta();

عند initialization وتغيير الـ theme.

اقتراحي: احذف:

vantaEffect
initVanta()
كل استدعاءاتها
وأي dependency خاصة بـ Vanta إن كانت موجودة في المشروع.

دي من أوضح عمليات التنظيف.

5. websockets موجود في requirements لكن لا يظهر استخدامه

في requirements.txt:

websockets

لكن الـ backend يستخدم FastAPI WebSocket نفسه، وليس import مباشر من package websockets.

غالبًا يمكن حذفه إذا لم يستخدمه جزء آخر من المشروع.

نفس الملاحظة تنطبق على dependencies مثل:

tenacity
fake-useragent
python-dotenv
beautifulsoup4
lxml
browser-cookie3
tldextract

لم أجد استخدامًا مباشرًا لها في ملفات Python الأساسية التي رفعتها.

مهم: قبل حذفها نهائيًا، اعمل search على المشروع كله، لأن الملفات المرفوعة هنا قد لا تمثل كل المشروع.

6. Imports غير مستخدمة

في main.py ظهر عندي على الأقل:

BackgroundTasks
glob

كـ imports غير مستخدمة في الملف.

وفيه أيضًا تكرار واضح:

import os

أكثر من مرة.

وكذلك imports داخل الملف نفسه يمكن تنظيمها بدل ما تكون موزعة.

🟠 مشكلة Architecture مهمة
7. عندك أكثر من مصدر للحقيقة بالنسبة للتصنيفات

في downloader.py:

CATEGORIES = {
    "Videos": ...,
    "Audio": ...,
    "Archives": ...,
    ...
}

بينما quick_add.js عنده نسخة أخرى:

CATEGORIES = {
    'Programs': ...,
    'Compressed': ...,
    'Video': ...,
    'Audio': ...,
    'Documents': ...
};




وهنا عندك اختلافات فعلية:

Videos vs Video
Archives vs Compressed
extensions مختلفة
Programs مختلفة
ISO مثلًا موجودة في أكثر من مكان بطريقة مختلفة

ده ممكن يعمل حالات UI يقول فيها شيء والـ backend يحفظ الملف في مكان مختلف.

الأفضل: يكون عندك مصدر واحد للتصنيفات، أو على الأقل JSON/config مشترك.

🟠 mini_progress.js فيه حاجات قابلة للتنظيف

API_URL موجود:

const API_URL = 'http://127.0.0.1:8000/api';

لكن الـ Mini Monitor الظاهر من الكود يعتمد على WebSocket وIPC أكثر من API.

فلو بحثنا عن استخداماته الفعلية ووجدنا أنه لا يستخدم في بقية الملف، احذفه.

كذلك os imported في نفس الملف، ويحتاج مراجعة استخدامه.

🟡 WebSocket reconnect محتاج تحسين

حاليًا عند disconnect:

setTimeout(connectWebSocket, 2500);

وفي حالة error:

ws.close();

وفي renderer.js نفس الفكرة تقريبًا لكن بـ 2 seconds.

المشكلة لو حصلت سلسلة failures طويلة، ممكن تعمل reconnect loops غير ضرورية.

أنا أفضل:

exponential backoff
حد أقصى مثل 30s
منع أكثر من reconnect timer في نفس الوقت
reset للـ backoff بعد successful connection.
🟡 Error handling فيه ابتلاع أخطاء أكثر من اللازم

مثلًا:

catch (e) {}

موجود في WebSocket في الـ Mini Monitor.

ده خطر أثناء التطوير لأنك ممكن يكون عندك JSON malformed أو bug حقيقي ومش هتعرف.

الأفضل:

catch (error) {
    console.warn('Failed to process WebSocket message:', error);
}

خصوصًا أن عندك أصلًا logging system.

🟡 مشكلة محتملة في stream_file

عندك:

for root, dirs, files in os.walk(BASE_DOWNLOAD_DIR):
    if rec.filename in files:
        return FileResponse(...)

ده معناه أن كل طلب stream ممكن يعمل scan على شجرة الـ Downloads بالكامل لو الملف لم يكن في المسار المتوقع.

مع عدد ملفات كبير، ده يصبح مكلف.

والأسوأ: لو عندك ملفان بنفس الاسم في مجلدين مختلفين، ممكن يرجع الملف الخطأ.

الأفضل: تخزن file_path الحقيقي في DB عند إنشاء/اكتمال download، وتستخدمه مباشرة.

🟡 مشكلة في Speed Limit

في normal downloader:

expected_time = len(chunk) / (GLOBAL_SPEED_LIMIT_KBPS * 1024)
await asyncio.sleep(min(0.5, expected_time))

دي ليست rate limiter دقيقة جدًا؛ لأنها لا تأخذ في الاعتبار الزمن الذي استغرقه تنزيل الـ chunk نفسه.

يعني لو الشبكة أصلًا بطيئة، أنت تضيف sleep إضافي بدون حساب معدل النقل الحقيقي.

الأفضل استخدام token bucket / monotonic timing based limiter.

🔵 حاجة عجبتني ومش محتاجة تغيير

في renderer.js عندك نظام جيد نسبيًا لتسجيل سرعة التحميل:

window.speedHistory[dl.id]

وتحافظ على آخر 20 tick فقط.

والـ backend عنده error logging جيد وملف log مع rotation/retention.
